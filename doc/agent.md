## 1. 文档定位

`doc/req/this.md` 的原始要求里有一句话定了产品形态：

> Agent时代应该只需要一个对话输入框、语音输入框。展示多层级任务，然后修正任务，也是通过输入框直接给建议。底层Agent维护任务树。

现在的实现没有做到这一点。本文档定义把「底层 Agent 维护任务树」真正落地需要什么，以及**哪些事 Agent 永远不许做**。

## 2. 现状盘点

以下是代码事实，不是文档说法：

| 能力 | 实际实现 | 位置 |
|---|---|---|
| 对话 | 单条消息 → 一次 chat completion → 返回一段文本。无历史、无工具、无第二轮 | `worker.go:181` → `openai.go:122` |
| 任务树生成 | 一次性返回 JSON 数组，字段靠 prompt 约束 | `openai.go:69` |
| 任务树修订 | 把现有任务序列化塞进 instruction，仍是一次性调用 | `worker.go:122-154` |
| 每日计划 | **模型完全不参与**，纯确定性算法 | `worker.go:155` → `app.go:466` |
| 辅助任务 | 硬编码的固定建议，不调用模型 | `worker.go:207` |
| 消息存储 | `Content` 是扁平字符串，承载不了工具调用和结构化内容 | `models.go:235` |

**结论：当前系统有一个不错的「LLM 调用器」，但没有 agent。**

需要同时明确的是，底座质量很高，不需要推倒：持久化 Agent Job、租约 + fencing token + attempt 校验、重试、取消、幂等键、ETag/If-Match 乐观锁、`Proposal` + `ApplyProposal` 的事务内重校验，这些都是一个真 agent 运行时需要的承载层。**本设计是在这个底座上加循环和工具，不是另起炉灶。**

## 3. 设计结论

| 能力 | 结论 | 优先级 |
|---|---|---|
| 多轮工具调用循环 | 做，本设计的核心 | L1 |
| 只读上下文工具 | 做 | L1 |
| 任务树提案工具 + 用户审批 | 做，替换现有一次性 JSON 路径 | L1 |
| 流式输出 | 做，见 ADR-0002 | L1 |
| 每日计划的 Agent 参与 | 做，但**只产出候选与理由，不决定最终取哪三个** | L2 |
| 坐标提案工具 | 做，复用 `lens.md` 已定义的语义 | L2 |
| 语音输入接入 agent | 做，转写结果进 composer 由用户确认后发送，不直接触发 agent | L2 |
| Agent 直接写业务表 | **不做** | — |
| Agent 自主定时行动（无人触发） | **不做** | — |
| 子 agent / 多 agent 编排 | **不做**，属 FastLabs 边界（`arch.md` §3.3） | — |
| 文件系统与代码执行工具 | **不做**，走 FastRead / FastWrite 集成边界 | — |

## 4. 五条不可破坏的不变量

Agent 运行时的全部设计都服从这五条。任何实现如果需要绕开其中一条，说明设计错了，不是不变量该改。

1. **Agent 不直接修改业务数据。**（`arch.md` §9.1）所有写操作产出 `Proposal`，用户确认后由 `ApplyProposal` 在事务内重新校验并落库。
2. **每日核心项最多三个，且这个上限由确定性程序强制，不由模型强制。**（`arch.md` §8.1、§10.1）Agent 可以推荐五个候选并说明理由，取几个、取哪几个由 `CreateDailyPlan` 决定。
3. **当日满足不等于底层任务完成。**（`arch.md` §7.4）Agent 不得提供任何直接把 `Task` 标记为 `completed` 的工具。
4. **模型输出是不可信输入。**（`arch.md` §12）工具参数必须经 JSON Schema 和领域校验；提案应用前必须重新校验所有权与 revision。
5. **跨用户数据绝不可达。** 每个只读工具都在 `user_id` 范围内执行，`user_id` 来自请求认证上下文，**永远不来自模型参数**。

## 5. 工具分级

这是本设计最重要的结构性决定：**工具不是「模型能调用的函数」，而是 application 层用例的受控投影。**

### 5.1 只读工具

直接执行，结果进模型上下文。强制按认证用户过滤。

| 工具 | 用途 |
|---|---|
| `list_goals` | 活跃目标与验收标准 |
| `get_task_tree` | 指定目标的完整任务树与当前 revision |
| `get_daily_plan` | 指定本地日期的计划与计划项状态 |
| `list_progress_events` | 近期进度证据，用于判断真实推进还是卡住 |
| `get_weekly_review` | 周复盘聚合，复用 `lens.md` §7 已实现的能力 |
| `list_stalled_tasks` | 长期无进展的任务 |
| `get_task_coords` | 任务在预设透镜下的坐标 |

### 5.2 提案工具

**不写业务表。**产出 `Proposal` 并以工具审批形式呈现，用户确认后才落库。

| 工具 | 产出 | 应用路径 |
|---|---|---|
| `propose_task_tree_patch` | create / update / move / supersede 操作数组 | `ApplyProposal`（`app.go:991`） |
| `propose_daily_plan` | 候选任务 + 每项最小行动 + 推荐理由 | `CreateDailyPlan` / `ReplanDailyPlan` 重新过滤排序取三 |
| `propose_task_coords` | 任务坐标与打分依据 | 遵守 `lens.md` §4：`pinned` 坐标不得被覆盖 |

### 5.3 禁止暴露

管理员操作、Provider 配置、设备 Token 的创建与轮换、用户与会话管理、直接修改 `daily_plan_items.status` 或 `tasks.status`、删除任何数据。

这些不是「暂时不做」，是**结构性禁止**：它们不出现在工具注册表里，因此不存在被 prompt 注入诱导调用的路径。

## 6. Agent 在每日计划中的位置

这一节单独写，因为最容易做错。

`arch.md` §9.2 已经定死了分工：

> Agent 负责理解和建议，程序规则负责最终过滤、排序和数量上限。

因此每日计划的流程是：

```text
Agent 读取上下文（活跃目标、可执行候选、近期进度、阻碍、周复盘、坐标）
  -> Agent 产出「候选任务 + 每项最小行动 + 推荐理由」并写入计划输入快照
  -> 确定性规则过滤、排序、去重、取前 0..3 项
  -> 用户确认后落库
```

三条约束：

- **Agent 的产出是输入快照的一部分，不是输出。** `arch.md` §9.2 要求确定性承诺针对完整输入快照成立，该快照必须包含 Agent 分析结果、schema 版本和内容哈希。
- **候选不足时不补占位任务。** `arch.md` §3、`func.md` 的核心产品判断：三个是注意力上限，不是必须填满的配额。Agent 的 prompt 必须显式包含这一点，否则模型天然倾向于凑满三个。
- **最小行动必须真的最小。** `req/this.md` 要求「最差情况只能搞不到半小时也要能完成」。提案里每个候选都必须带一个 5–15 分钟内可以开始的具体动作，缺失则该候选无效。

## 7. 审批模型

assistant-ui 的工具审批与 FastTask 的 `Proposal` 是同一件事的两半，本设计把它们对接起来：

```text
模型发起提案工具调用
  -> 服务端创建 Proposal（status=pending），不写业务表
  -> 以待审批的工具调用形式推送给前端，附带结构化 diff
  -> 用户在对话里直接确认或拒绝
  -> 确认：ApplyProposal 在事务内重校验所有权 / revision / 循环 / 字段约束后落库
     拒绝：Proposal 置为 rejected，结果回灌模型上下文，模型可据此重新提案
```

三条规则：

- **高影响变更一律需要确认。** `arch.md` §16 建议 MVP 阶段任务树结构性变更全部确认，本设计采纳，不做「低风险自动应用」的例外。
- **迟到的审批必须被拒绝。** 用户确认时如果 tree revision 已经变化，返回 `412` 并把提案标记为冲突，不静默覆盖（`arch.md` §9.1）。
- **拒绝是有价值的信号。** 拒绝理由要回灌模型上下文，这正是「对话式修正任务树」相对一次性生成的核心优势。

## 8. 会话、运行与作业的关系

三个概念不要混淆：

| 概念 | 含义 | 生命周期 |
|---|---|---|
| **Thread（会话）** | 用户与 agent 的一条持续对话，承载消息历史 | 长期，用户可有多条 |
| **Run（运行）** | 一次「用户发言 → 模型多轮工具调用 → 产出回复」的完整过程 | 秒到分钟级，可取消、可续流 |
| **AgentJob（作业）** | 已有的持久化作业记录，承载租约、重试、取消、fencing | 与 Run 一一对应 |

Run 复用 AgentJob 的租约与 fencing 机制，不新建一套并发控制。断线重连时，客户端凭 thread 拿回服务端保留的状态和 `runId` 续流，而不是重新发起一次运行——这既是 PWA 移动端的刚需，也让「关掉浏览器再打开，任务还在跑」成立。

## 9. 不做什么

- **不做自主 agent。** 没有人类触发就没有 agent 运行。定时任务只做 `arch.md` §10.3 列出的维护工作，不做「AI 自动帮你重排今天」。理由是 `plotminder/product.md` 已经确立的产品原则：用户判断是主角，系统建议是配角。
- **不让 agent 碰墨水屏和 Panel 契约。** 设备只读投影和 Panel 摘要的契约保持不变（`arch.md` §7.7、§7.8）。
- **不做通用 DAG 编排。** `arch.md` §3.3 的非目标原样保留。
- **不引入向量库和 RAG。** 上下文来自结构化业务数据，不是文档检索。出现真实需求时单独立 ADR。

## 11. 待确认

以下各项已给出实现时可直接采用的默认值，**不阻塞实现**；接入真实模型后按观测调整。

| 事项 | 默认取值 | 何时重新评估 |
|---|---|---|
| 单个 Run 的轮数上限与 token 预算 | 8 轮 / 180 秒墙钟（`agent-impl.md` §6） | 接真实模型并观察一周后 |
| 对话是否按目标分线程 | 复用现有 `Conversation.goal_id`（`models.go:229`），可选绑定 | 用户反馈目标间上下文串味时 |
| 提案被拒后是否自动重试 | **不自动重试**，等用户下一句话 | 若用户普遍需要手动追问「那你再想一个」 |
| 语音转写后是否可直接发送 | **保留现有行为**：填进输入框由用户确认（`App.tsx:240`） | 用户反馈多一步确认很烦时 |
