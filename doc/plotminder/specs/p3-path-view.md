# Feature Spec: P3 Path View

**Phase**: P3
**Milestone**: Closed Beta
**Status**: Draft
**Created**: 2026-05-19
**Constitution Compliance**: v1.0.0
**Dependencies**: P0, P1, P2

---

## 1. 概述

P3 实现 Plotminder 与所有竞品的**核心差异化能力**:基于坐标的下一步路径推荐。三件事:**DAG 依赖编辑、路径推荐算法、The Decide 用户时刻的可视化**。

P3 是 demo 视频应该围绕拍摄的 phase——10 点钟用户问"现在做啥",Plotminder 在地图上画出 5 步推荐路径,每段附一句理由。

成功标志:**一个用户能在不看 deadline 的前提下,只靠 view 的语义维度和 task 依赖关系,获得一条合理的、可解释的执行路径**。

---

## 2. 用户故事

- **US-P3-1** 作为用户,我能在地图上点击一个 task A,然后点击 task B,把 B 标记为依赖 A(在 A 完成前 B 不可激活)。
- **US-P3-2** 作为用户,我能看到节点之间的依赖关系以箭头形式呈现(可开关显示)。
- **US-P3-3** 作为用户,我能在任何时刻点击"推荐下一站"按钮(或快捷键),系统立即在地图上高亮下一步 task 并画出后续 3–5 步路径。
- **US-P3-4** 作为用户,我能看到每段路径上的一句话理由,理解为什么是这个顺序。
- **US-P3-5** 作为用户,系统**绝不**根据 deadline 推断路径——优先级完全由当前 view 的坐标决定。
- **US-P3-6** 作为用户,当被推荐的 task 仍被未完成依赖阻塞时,推荐项明确标注"被 X 阻塞,X 完成后激活"。
- **US-P3-7** 作为用户,我可以拒绝当前推荐(点击"换一个"),系统提供下一个 frontier 候选。
- **US-P3-8** 作为用户,我可以配置推荐路径的步数(默认 5,可调 3–10)。

## 3. 功能需求

### 3.1 DAG 依赖编辑

- **FR-P3-001** 用户能在地图上创建 task 间的依赖边:
  - 长按节点 → 拖向另一节点 → 释放,创建依赖
  - 或在 detail panel 中显式添加"依赖于"字段
- **FR-P3-002** 系统检测并阻止环路依赖(在 P0 已建模的 `dependency.detect_cycle` API 基础上)。
- **FR-P3-003** 依赖边以箭头显示(从被依赖者指向依赖者),颜色低饱和度,不喧宾夺主。
- **FR-P3-004** 用户能开关依赖边显示(顶栏 toggle)。
- **FR-P3-005** 删除依赖:点击边 → Delete 键;或在 detail panel 中移除。
- **FR-P3-006** 依赖关系是 task-level,跨所有 view 全局生效(宪章 III.3,依赖属于跨 view 共享状态)。

### 3.2 路径推荐算法

- **FR-P3-007** 算法严格按宪章 II.3 的优先级链执行:
  1. **拓扑排序**:被未完成依赖阻塞的 task 不进入候选
  2. **Pareto frontier**:在当前 view 上,frontier = 没有别的活跃 task 在所有轴上都比它更接近 ideal corner
  3. **距 ideal corner 的欧氏距离**:frontier 内部排序
  4. **用户为各轴指定的权重**:平局时按加权欧氏距离打破
- **FR-P3-008** 算法**完全不考虑** `deadline`、`created_at`、`scheduled_at` 等时间字段(宪章 II.2、II.3)。
- **FR-P3-009** 算法返回:`PathRecommendation { steps: [Step], view_id, generated_at }`,其中 `Step` 含 `task_id`、`rank`、`rationale`、`blocked_by: [task_id]`(若被阻塞)。
- **FR-P3-010** 算法在 Go core 中实现,提供同步 API(纯计算,无 LLM 调用)。
- **FR-P3-011** 若候选数量 < 推荐步数(例如只有 3 个活跃 task 但用户要 5 步),返回所有候选 + 一个明确信号"已经是全部"。

### 3.3 推荐理由 (Rationale)

- **FR-P3-012** 每个推荐 step 必须附一句理由。理由的生成规则:
  - 默认使用**模板化**理由(无 LLM):
    - "{view_name} 上 frontier 最右上"
    - "重要 92 / 紧急 88 — 距 ideal corner 最近"
    - "被 [task X] 阻塞,X 完成后激活"
  - 用户可在 Settings 启用"LLM 增强理由",此时 LLM 在模板基础上重写为更自然的语言
- **FR-P3-013** LLM 增强理由必须**保留所有数值与依据**,不允许 LLM 虚构原因。

### 3.4 The Decide 用户时刻可视化

- **FR-P3-014** "推荐下一步"触发方式:
  - 顶栏按钮"现在做啥"
  - 快捷键 Cmd/Ctrl + Enter
  - 完成一个 task 后,如果用户开启"自动推荐下一站",立即推荐
- **FR-P3-015** 推荐结果在地图上的可视化:
  - 下一站 task 高亮(动画脉冲、放大、明亮边框)
  - 后续 step 用编号 ① ② ③ ④ ⑤ 标注
  - 路径线连接各 step(贝塞尔曲线或直线,可配置)
  - 每段附小字 rationale,鼠标 hover/点击展开完整
- **FR-P3-016** 推荐 panel(侧栏)同步显示列表视图,便于阅读所有 step。
- **FR-P3-017** "换一个"按钮:用户拒绝当前下一站后,算法剔除被拒 task 再次计算,生成新推荐(被拒决策本地保留至当日 24:00,避免无限循环)。
- **FR-P3-018** "接受并开始":点击后下一站 task 自动切换状态为 `doing`(这是用户主动确认,不违反 I.3)。

### 3.5 配置

- **FR-P3-019** Settings → Path Recommendation:
  - 推荐步数(默认 5,3–10)
  - 路径线样式(贝塞尔/直线)
  - 是否启用 LLM 增强理由
  - 是否完成任务后自动推荐下一站
  - 是否在推荐时考虑被 archived 的 task(默认否)

## 4. 非功能需求

- **NFR-P3-001** 路径计算 P95 < 100ms,即使在 2000 节点 + 500 依赖边的 workspace 上。
- **NFR-P3-002** 路径推荐结果完全 deterministic——同样的数据、同样的 view、同样的权重,必产生同样的推荐(便于测试与用户信任)。
- **NFR-P3-003** 路径推荐必须可被纯单元测试覆盖(Go core 层,无 UI 依赖)。
- **NFR-P3-004** LLM 增强理由是 opt-in,默认关闭(避免不必要的网络调用)。

---

## 5. 验收标准

- **AC-P3-1** 在 20 个 task + 5 条依赖边的 mock 数据集上,推荐路径符合手工算出的 frontier 顺序。
- **AC-P3-2** 故意构造环路依赖,系统拒绝创建,弹出明确错误提示。
- **AC-P3-3** 给两个 task 设置相同坐标,系统按用户配置的轴权重打破平局,且重复多次推荐结果完全一致(deterministic)。
- **AC-P3-4** 给某 task 设置一个 deadline = "今天",推荐路径**不**因此把它排到第一(除非用户已把"时间紧迫程度"显式设为轴)。
- **AC-P3-5** 切换 view 后,同一组 task 推荐路径不同(因为 frontier 与 ideal corner 不同)。
- **AC-P3-6** 完成下一站 task 后,如开启自动推荐,新推荐立即出现且与刚完成的 task 无关。
- **AC-P3-7** 模板理由准确反映算法决策依据(可与手工对比 frontier 计算)。
- **AC-P3-8** 关闭 LLM 增强后,所有理由来自模板,无网络调用。

## 8. Constitution Alignment

| 宪章条款 | 关系 | 处理 |
|---------|------|------|
| II.1–II.5 (坐标驱动,非时间驱动) | **核心落地** | FR-P3-008、AC-P3-4 显式禁止 deadline 进入算法 |
| II.3 (优先级链顺序) | **直接落地** | FR-P3-007 一字一句对齐 |
| I.1–I.2 (用户判断主权) | **核心保护** | 推荐永远是建议;用户可拒绝、换一个、手动覆盖路径 |
| I.3 (永不偷偷改数据) | **关键保护** | "接受并开始"必须用户**主动点击**才切换状态;**绝无**"系统自动开始下一站" |
| 决策启发式 #2 (是否让时间偷偷成为隐形主轴) | **核心检查** | 任何后续 PR 想往算法中加 deadline 系数都必须先修宪 |

**潜在张力点**

- **关于"完成任务后自动推荐下一站"**: 这是 FR-P3-019 的可选项。严格说"自动推荐"也是一种自动化行为。处理:推荐**只是计算并显示**,不会自动改变任何 task 的 status;因此符合宪章 IV(看见 > 自动化),而非 I.3 所禁止的"自动改数据"。
- **关于 LLM 增强理由可能虚构**: 已在 FR-P3-013 显式约束 LLM 只能在数值基础上改写,不能引入新依据。需要 prompt 层强约束 + 测试用例覆盖。

## 9. 开放问题

- **OQ-P3-1** Pareto frontier 在大规模数据(5000+ 节点)下的高效计算策略:Kung 等高级算法 vs 简单 O(n²) 配合 frontier 缓存?
- **OQ-P3-2** 路径线的视觉风格:贝塞尔曲线美但容易交叉混乱;直线清晰但不优雅。需要设计验证。
- **OQ-P3-3** 推荐路径中"被阻塞"的 task 是否显示在路径上?(目前 FR 假设显示,但视觉上可能让路径感弱化)
- **OQ-P3-4** 推荐路径的持久化:用户接受路径后,是否记录"推荐历史"供 Reflect 阶段分析?(可能跨入 P5 范围)
